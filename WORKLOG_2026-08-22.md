### The bottleneck, exactly

`cell_69.py:428` and `cell_75.py:385`:

```python
pid = PROPERTY_TO_WIKIDATA.get(prop.lower())
if not pid:
    return {"verdict": "UNVERIFIABLE", ...}   # <-- 25/34 B3 claims die here
```

Note this fires **before** `resolve_entity` is called — so for unmapped
properties we never even learn whether the entity resolves.

### Root cause (5-Why)

TEMPORAL coverage 0% → 25/34 hit unmapped property → `PROPERTY_TO_WIKIDATA` is a
static hand-written dict → design assumed claim predicates form a small closed
set → free-text claims produce open-vocabulary predicates →
**ROOT: predicate mapping is treated as a LOOKUP problem when it is a
MATCHING/RETRIEVAL problem.**

### Design

1. Resolve entity FIRST (unconditionally) — decouple from property mapping.
2. Fetch the entity's **full statement set** in one `wbgetentities props=claims`
   call. `fetch_candidate_meta` already uses `wbgetentities`, so this reuses
   proven, cached HTTP machinery.
3. **Filter candidate PIDs by datatype** against the claim type
   (TEMPORAL→`time`, EA→`wikibase-item|string|monolingualtext`,
   QUANTITATIVE→`quantity`). Cheap, strong prior, big precision win.
4. Rank surviving PIDs against the claim predicate with the same
   lexical-tier + SBERT scheme already proven in `resolve_entity`.
5. Keep the static map as a **fast path / prior, never a hard gate**.
6. Emit `property_route` (`mapped` | `matched` | `gap`) + `property_score` so the
   next bottleneck stays diagnosable (observability point from thoughts.txt).

### Why this is the right fix

Both known B3 bugs are covered — the target property is sitting in the
entity's statement set in each case:
- Panama Canal **Q7350** → `P1619` = 1914-08-15 (map said P571, which Q7350 lacks)
- Rosetta Stone **Q48584** → `P186` = granodiorite (map said P527, which it lacks)

i.e. the fix the architecture already needed would also have prevented the bug
that was just spent time fixing.

### Three bugs found in my own first implementation

1. **Score-range import.** Reused `0.5*tier + 0.5*sim` from `resolve_entity`.
   Predicates and property labels come from different vocabularies, so tier is
   legitimately 0 for most correct matches — capping the score at 0.50 and
   putting the 0.60 threshold out of mathematical reach. P1619 and P186 both
   ranked #1 and were still rejected. Fixed: tier is now a bonus over
   similarity, never a cap.
2. **Claim-text dilution.** Query was `f"{pred}. {claim_text}"`. The predicate
   is a property *name*; so are Wikidata labels. Appending the full sentence
   mixes granularity. Measured on Q48584/'consists_of': P186 falls 0.686 -> 0.397
   and nearly loses rank to P1343. Fixed: predicate only.
3. **External-ID leakage.** `external-id` was in the EA datatype whitelist, so
   'tallest_peak_in' matched P3109 (Peakbagger ID) = "10640" against claimed
   "Asia". Fixed: EA datatypes are now `{wikibase-item, monolingualtext}` only.

### Structural guards added (not per-claim patches)

* **Directional veto** — SBERT scores topical relatedness, not direction.
  'part of' (P361) and 'consists of' are near-identical in embedding space and
  opposite in meaning. Caused 7 confident-wrong matches (human liver, Lobules,
  Denali, Mount Vinson). Meronym predicates now reject holonym properties.
* **Superlative-containment veto** — 'tallest_peak_in' is modelled on the
  *container* (X's P610 == subject), not on the subject. Forced to honest gap
  pending an inverse-lookup path.
* **Core-term guard (TEMPORAL)** — 'year'/'date'/'time' scaffolding dominates
  the embedding and makes unrelated dates look alike. Stripping it separates
  'decipherment' vs 'birth' (0.283) cleanly.

### Threshold calibration — confirmed by data, not guessed

`PROPERTY_THRESHOLD = 0.60` **kept**. Lowering to 0.55 would admit
`Rosetta Stone publication_year -> P575 (time of discovery or invention)`,
which is wrong. Correct matches span 0.649–0.925.

Note the earlier naive run proved threshold tuning **cannot** fix this alone:
correct matches spanned 0.686–0.925 and wrong ones 0.649–0.746 — overlapping.
Structural guards were mandatory.

### Architecture decision: NOT NLI (settled, with authority)

CLAUDE.md listed QUANTITATIVE as "architecture undecided (text+NLI fallback vs.
stay UNVERIFIABLE)". Closed **against NLI** on FinGround (`2604.23588v1`),
verbatim: *"Generic NLI fails on ratio and margin verification even when the
correct evidence passage is retrieved, because the failure is in reasoning rather
than retrieval."* A number claim is checked by extracting a number and comparing
it. See `reference/paper_findings_2026-08-22.md` §4.

Three subtypes, mirroring FinGround: **NUMERICAL** (verified now),
**COMPARATIVE** (honest gap — needs multi-entity retrieval), **COMPUTATIONAL**
(honest gap — needs formula + operands). This takes the taxonomy 5 → 7 types,
inside FinGround's supported granularity band (6-type beats 3-type by 4.3 F1;
10-type p = 0.23, no significant gain).

Hedge detection runs **before** any numeric comparison — FinGround: *"Hedged
financial language ('approximately,' 'roughly') drives 52% of false positives."*
A hedge is parsed into a comparison **operator** (GE / LE / APPROX / EQ), because
"over 20,000 deaths" is TRUE at 25,000 and FALSE at 15,000; testing it for
equality is a category error.

### Four defects found and fixed BEFORE any execution

Found by reading `property_resolver.py` in full to verify the 10 cross-module
imports (per the CLAUDE.md standing rule — don't assume, verify), then by
desk-tracing all 29 gold rows.

1. **Superlative over-routing.** `_RANK_MARKERS` lumped superlatives in with
   explicit rank words, so `highest_elevation` routed to COMPARATIVE — discarding
   the single biggest winnable cluster (7 Batch-3 mountain elevations, all
   P2044). Split into `_EXPLICIT_RANK` (always COMPARATIVE) and
   `_SUPERLATIVE_MARKERS` (COMPARATIVE only when no measurable magnitude is
   stated).
2. **Uncached `wbsearchentities`.** `--sensitivity` would have fired 8 identical
   uncached HTTP calls per claim at `POLITE_DELAY = 1.1` each. Added a
   `search__{subj}` cache key; failures never cached (the cache-poisoning bug
   already fixed in RELATIONAL).
3. **Wrong perturbation direction for LE claims.** Perturbing only upward makes
   an upper-bound claim *easier* to satisfy, so a working verifier would look
   like it never flips. Added `sign = -1.0 if op == "LE" else 1.0`, and the
   operator is re-injected explicitly (`"over "` / `"up to "` /
   `"approximately "`) so rewriting `value` cannot silently downgrade a bound
   claim to an equality claim.
4. **Missing disambiguation context in entity resolution.** ctx was built from
   `secondary` only; CLAUDE.md records bare "Denali" scoring 0.590 against
   *"album by Denali"*. ctx is now `[claim_text] + secondary strings`. This does
   **not** contradict property_resolver's "predicate only" lesson — that lesson
   is about matching a predicate *name* to a property *label*; entity resolution
   scores candidates on *descriptions*, which sentence context genuinely informs.
   Honest caveat: `RESOLUTION_THRESHOLD = 0.60` was calibrated with a different
   ctx construction, so here it is an inherited starting point, not a
   calibration.

### Two further defects found by desk-tracing all 29 gold rows

5. **False hedge from a measurement datum.** B3_01_C09 is *"locks lift ships 85
   feet **above** sea level"*. Scanning the whole sentence for hedges read
   "above" as a lower bound, converting an exact figure into `actual >= 85`.
   Fixed structurally: hedges are now matched **positionally** — only in a
   40-char window immediately *preceding* the quantity, with `_DATUM_PHRASES`
   ("above/below sea level", "above ground", "above average") stripped first.
   The window anchors on **this claim's numeral**, not the first number in the
   sentence, so *"The 2014 to 2017 event affected over 70 percent"* windows on
   70 and not on 2014. Explicit `secondary.precision` fields are still honoured
   (B3_11_C02 carries `{"precision": "approximately"}`, which has no adjacency
   to exploit). Three regression cases added to `--selftest`.

6. **Confident-right-for-the-wrong-reason (the serious one).** `Q30` (United
   States) carries many `quantity` statements, so `number_of_active_satellites`
   can reach **P1082 (population, ~3.4e8)**. Both are dimensionless counts, so
   `compare()` cannot refuse on units — and the GE-hedged claim "over 5,000"
   would return **TRUE against population**. A right verdict from wrong
   evidence is invisible in aggregate accuracy and strictly worse than a gap.
   Fixed with a **QUANTITATIVE core-term guard** (`qty_core_guard`,
   `QTY_CORE_THRESHOLD = 0.35`) that strips counting scaffolding
   (`number/count/total/amount/...`) and re-checks the winner on content words
   alone: "active satellites" vs "population" fails; "elevation" vs "elevation
   above sea level" passes. Deliberately placed **in this module, not in
   `property_resolver`**, whose guard is gated to `claim_type == "TEMPORAL"` and
   strips a *time* vocabulary — so TEMPORAL/EA behaviour is unchanged. Applied
   only to `route == "matched"`; a static-map hit is a human decision and is not
   second-guessed.

### The evaluation problem, stated up front

28 TRUE / 1 FALSE means **an unconditional "TRUE" scores 96.6%.** Worse, the one
gold-FALSE claim (B3_02_C09, renewable capacity "3,372 GW", an IRENA statistic)
has subject `renewable capacity`, which is not a Wikidata entity — so the
verifier will honestly return UNVERIFIABLE on **the only claim that could
demonstrate detection**.

Therefore: **any accuracy figure from `--diagnose` on Batch 3 measures the base
rate, not detection ability.** Coverage is meaningful; raw accuracy is not. This
is recorded prominently in the module docstring so it cannot be quoted out of
context later.

`--sensitivity` is the answer: perturb each *successfully verified* value by a
known percentage (0.1% → 50%) and record where the verdict flips. The label of a
perturbed claim is certain **by construction**, so this measures discrimination
with no gold negatives and no extra API cost once values are cached. Caveat
recorded in the function docstring: synthetic perturbations are not real
hallucinations.

### 5a. `current/consolidate_claims.py`

Merges the four sets into one CSV under a 24-column unified schema
(`CORE` + `EXTRA`). Guards against four traps found by inspection, each of which
a naive `pd.concat` would hit silently:

* **Four schemas** (14 / 15 / 19 / 12 cols), and Batch 3 interleaves
  `pair_id`/`pair_incomplete` *between* `flagged` and `subject` → column position
  is not stable, so the loader uses `csv.DictReader` **only** and never indexes
  by position.
* **`flagged` has three encodings** — `TRUE`/`FALSE` (Batch 1), `True`/`False`
  (Phase 2, Batch 3), absent (negatives) → normalised to `true`/`false`/`""`.
  This one bit me live during the audit: a router grep returned 0 matches and
  looked like a bug, but was the encoding difference.
* **`TRUE`/`FALSE` is overloaded** across `flagged` and `gold_verdict` → verdicts
  are read by column name, never by regex.
* **Finding 3 is enforced, not just documented:** `--routing` prints
  `REFUSED batches (gold_type seeded from `type`, so any score is 100% by
  construction)` and scores only batches with `gold_type_independent == true`.

Every expected row count / labeled count / verdict distribution from Step 4 is
hardcoded in `SOURCES[*]["expect"]` and checked on load; a mismatch aborts before
writing. `claim_id` disjointness is enforced. `--write` **refuses to overwrite**
an existing output.

### 5b. `current/metrics.py`

Reusable metrics module — implements `paper_findings` action items #3, #4, #5 in
one place so no verifier reimplements them. `wilson`, `fmt_ci`, `per_class_prf`,
`macro_f1`, `mcc` (binarised on FALSE = "is a hallucination"), `unknown_rate`,
`degenerate_baselines`, `risk_coverage`, `aurac`, `selective`, `report`,
`curve_table`.

The design point worth preserving: **`UNVERIFIABLE` means two different things**
and merging them is a real methodological error. Gold UNVERIFIABLE (29 claims) =
not checkable in principle; predicted UNVERIFIABLE = this verifier could not
reach evidence. So `report()` prints two views side by side and never merges
them — a **selective view** (coverage + accuracy on covered only, where a
confident verdict on a gold-UNVERIFIABLE claim is counted as an error and
surfaced as `overreach`), and a **three-way view** (RealFactBench-style, with
UNVERIFIABLE as a real class). It also auto-warns when gold negatives are 0
("use controlled perturbation") or <10 ("F1(FALSE) is extremely high-variance").

Deliberately **not** framed against Factcheck-Bench / OpenFactCheck scoring,
which fold NEI into False and thereby make honest abstention unscoreable.

### A design error caught mid-write, and what it revealed

The first draft called `pr.resolve_property_values(subject, ...)` and read a
verdict off the result. Checking the actual source killed all three assumptions:

* the first parameter is a **`qid`**, not a subject;
* the kwarg is `claim_text=`, not `ctx=`;
* it returns `{pid, values, route, score, detail}` and **never produces a
  verdict at all** — it stops at "here are the values for the matched PID".

So `property_resolver` is a property-*matching* layer, nothing more. Two things
follow, and the second is the important one:

1. **The comparison step had no home.** Turning matched values into TRUE/FALSE
   lives only inside notebook cells 69/75. `compare_tier1()` is now that step,
   standalone. It deliberately ranks a **mismatch below a match**
   (`TIER1_MISMATCH = 0.70` vs `TIER1_FLOOR = 0.80`): a match means the graph
   asserts exactly this, but a mismatch may only mean Wikidata is incomplete or
   the property is multi-valued. Cells 69/75 already take that risk silently;
   this makes it explicit and ranks it lower on the risk-coverage curve.
2. **`property_resolver.diagnose` resolves QIDs by first `wbsearchentities`
   hit.** That is honest for a diagnostic measuring only the property layer — it
   says so in a comment — but it is a close cousin of the heuristic behind the
   QID bug (Panama Canal → Q498979 *Panama Canal Zone*; Rosetta Stone → a
   British punk band). **Had the hybrid inherited it, step (a) would have
   silently undone the 2026-08-21 fix.** So `resolve_fn` has **no default**: with
   no resolver supplied, tier 1 is skipped entirely rather than falling back.
   There is a comment saying never to add one.

That is the third time on this project that reading the source contradicted a
reasonable assumption about it — same lesson as the standing rule, applied to
function contracts rather than to files.

`verify_hybrid(row, cache, resolve_fn, tier2_fn, compare_fn)`. `resolve_entity`

### The new hazard: the date-adjacency trap

RELATIONAL does not face this. TEMPORAL/EA claims are `(subject, property,
value)` assertions, and a lead paragraph about the subject usually contains
**several** dates. NLI entails on topical overlap, so a passage naming "Panama
Canal", "1903" *and* "1914" entails both "completed in 1914" and "completed in
1903" — the model is scored on relevance, not on which value the claim picked.
Three gates, none of them NLI:

1. **Value-presence** — the claim's `value` must occur in the winning passage.
   Entailment without it is topical overlap → UNVERIFIABLE.
2. **Distractors** — same-shape competitors in that passage (other years; other
   numbers within 0.2×–5× magnitude) mean the evidence does not single out the
   claim → UNVERIFIABLE.
3. **Confidence ceiling** — `TIER2_CEILING = 0.65 < TIER1_FLOOR = 0.80`, so
   risk-coverage curves rank structured evidence above textual inference and an
   operating point can be chosen that takes tier 1 only.

A tier-2 `FALSE` is accepted only when it is *coherent*: contradiction **with the
claimed value absent** from the evidence. Contradiction while the value is
plainly present is incoherent and is refused.

### Why `--sensitivity` is the only real test here

**TEMPORAL and EA have zero gold negatives across all 34 Batch 3 claims.** A
fall-through that emitted TRUE for everything it touched would score **100%
accuracy** and coverage would look transformed. `--diagnose` therefore prints
`THAT ACCURACY IS NOT EVIDENCE` whenever the slice has no negatives.
`--sensitivity` perturbs each verified value shape-preservingly (`1914`→`1919`,
`8,848`→`12,387`) and requires the verdict to **flip**; a perturbed claim's label
is certain by construction. Flip rate is reported **per tier**, and a tier-2 flip
rate below 100% prints `DO NOT INTEGRATE` — that is the signature of scoring
topical relevance rather than truth.

Wikipedia paragraph goes straight past the model's window. This also silently
degrades the *routed* results — over-long premises dilute entailment.

  * `harden_native()` pins OMP/MKL/OpenBLAS/veclib/numexpr to 1 thread and sets

    each row's `method` field, and **the same cap must be applied when the routed
    side is re-run** or the two halves see different premises
  * `--nli-check`: loads BART and runs three inferences of growing premise length
    (short / 1200 / 6000 chars). Bisects the crash in seconds instead of paying
    for Gemini + Wikipedia + SBERT first. If 'short' dies it is threading; if
    only 'long' dies it is the position-embedding overrun

## Step 12 — cache seeding was only half-doing its job (2026-08-22, late)

The author's `zip` warned `name not matched: current/relational_cache.json`. That

| `title__{subject}` | singular | 3e has `titles__{query}__3` | no; re-searching is cheap |

## Step 16 — three resolver bugs; QUANTITATIVE gets its first validated result (2026-08-23)

Task #8 was "add a prominence prior". It turned out to be three bugs, and the
prominence prior was the least important of them.

### Bug A — identity score cannot break ties (the one on the task)

`score = 0.5*TIER_NORM + 0.5*sim` awards tier 3 to *any* entity whose label is
literally "Mount Everest", so the mountain and a stub both land near 0.5+0.5·sim
and the sort picked whichever won by a hair.

Fixed with a prominence tie-break on **sitelink count**, `RESOLUTION_TIE_BAND =
0.10`, applied among candidates within the band of the leader. **Prominence never
enters the number compared to `RESOLUTION_THRESHOLD`** — that is the safety
property and the reason the 2026-08-21 calibration survives untouched: a famous
wrong entity cannot be promoted past 0.60 by being famous. "China" 0.510, SpaceX
Starlink 0.547 and Denali-the-album 0.590 all still fail. The band is also below
0.17 = 0.5·(TIER_NORM[3]−TIER_NORM[2]), so a tier difference can never be tied
away.

### `current/make_negatives.py` — and three bugs it had first

Primary operator is **cross-substitution**: give claim A the value that truly
belongs to claim B, same property. Plausible by construction (a real,
correctly-formatted value of that kind — which is how LLMs actually fail), false by
construction, and assumption-free (every value comes from the corpus).

**Bug 1 — text cross-substitution is unusable.** Grouping by property *name* is not
grouping by *domain*, so `composition` pooled the liver, the Rosetta Stone and
CRISPR together:

    "The human liver is divided into right and left lobes."   <- STILL TRUE
    "The Rosetta Stone is a two primary lobes."               <- broken
    "The CRISPR-Cas9 system consists of the granodiorite stele."

Restricted cross-substitution to **numeric values only**. Text-valued claims now go
to `negatives_needing_manual_authoring.csv` instead of being silently corrupted or
silently dropped.

**Bug 2 — the scaler accepted anything containing a digit.** `"Cas9 protein and a
guide RNA"` → scaler found the 9, ×1.01, rounded back to 9, emitted a claim
**identical to the original but labelled FALSE**. `"September 15, 2008"` → scaled
the 15, rounded back, only a comma moved. Added `is_pure_quantity()`: one number,
no month names, only known unit/hedge words.

**Bug 3 — no final check.** Added `validate()`, which rejects any row whose claim
equals its base, differs only in punctuation/whitespace, or whose value is
unchanged after numeric normalisation. **It caught 6 more.**

Why these three mattered more than they look: a still-TRUE row labelled FALSE is
undetectable downstream — when a verifier disagrees with it, nothing distinguishes
a verifier bug from a label bug. It would have quietly corrupted every measurement
the negatives exist to enable.

### Design choices that matter

  * **A missing verdict is NOT an abstention.** TEMPORAL/EA and QUANTITATIVE have

  * **No rate is printed without its coverage.** 8 unverifiable + 2 TRUE is not "0%
    hallucination", it is 80% unmeasured.
  * **Dual-emit pairs collapse to one unit, worst verdict wins.** FALSE dominates
    TRUE: a genuine source attached to a false assertion still makes the response
    wrong, and letting the source's TRUE cancel the fact's FALSE would hide the exact
    failure dual-emit exists to expose. (Only 8 claims carry a `pair_id`, so the
    effect is small here — but the rule has to be right before the corpus grows.)

    (73.9% accurate) does not read like one verified by tier-1 Wikidata.

| tracks ground truth | **−1.8%** | **+6.0%** |

Routed flags fewer responses, consistent with its higher per-claim precision.

### THE UNCOMFORTABLE PART — routed fails the sanity check

Responses containing >=1 gold-FALSE claim should score *worse* than those containing
none. Non-routed separates them by **+6.0%** (correct direction). Routed separates
them by **−1.8%** (wrong direction, i.e. no signal).

Plausible mechanism, and it is the thesis's central tradeoff appearing at a new level:
**routed abstains on exactly the claims that matter.** Where the non-routed pipeline
guesses FALSE and is occasionally right, routed reports "no Wikidata property matched"
and stays silent — so its response score correlates *less* with ground truth despite
being more precise per claim. **Honest abstention means not flagging the bad
paragraph.**

**Do not report this as a finding yet.** Only 8-9 responses contain a negative and 12-13
negatives exist in total, so both separation figures are noise-dominated at this n. It
is a hypothesis with a clear test: balanced negatives per response, which is exactly
what Block D (FActScore, 50 S / 50 NS) supplies. If the sign persists there, it is a
real and important limitation of high-precision verification at the document level and
belongs in the thesis. If it flips, it was noise.

### Two bugs found by inspecting the disagreements, not the aggregate

Nine of the first run's 12 wrong verdicts shared one root cause, and one was a real
comparison hole. Both were invisible in the headline number.

**Bug A — TEMPORAL compared years only.** `FS_0094` claimed "born on May 5, 1987";
Wikidata holds `1987-03-05`. Same year, different month, verdict TRUE. Fixed by adding

1987-03-05, because demanding month/day would invent a requirement the claim never made.
5/5 on the date test cases.

**Bug B — EA comparison was lexical only.** The claim states an instance or paraphrase;
Wikidata stores a category; they share no token:

    "He was a columnist."      vs journalist, opinion journalist
    "had a political career."  vs politician
    "a fervent mix of rap"     vs Australian hip-hop
    "He sang in a group."      vs singer

All semantically TRUE, all reported FALSE. Added a **semantic tier** to
`compare_tier1` via an injected `sim_fn` (SBERT), with a deliberate asymmetry:
`>= EA_SEMANTIC_MATCH (0.55)` -> TRUE at 0.74 confidence (below `TIER1_FLOOR`, since a
paraphrase match is weaker evidence than a lexical one); `>= EA_SEMANTIC_NEAR (0.33)`
-> **UNVERIFIABLE, not FALSE**. That last choice is the point: "Wikidata says something
closely related but not identical" is evidence of granularity mismatch, not of
falsehood — the same principle as the ISRO mismatch guard.

`sim_fn` is **injected, not imported**, so `hybrid_fallthrough`'s 35 offline selftests
still run with no model and still pass ALL PASS.

## Step 27 — Router tie-break ablation (2026-08-24): HYPOTHESIS REFUTED

**Files:** `current/router_ablation.py`, `current/router_ablation_results.csv`
**Reverse:** `rm -f current/router_ablation.py current/router_ablation_results.csv`

**Hypothesis.** The deployed prompt says *"PRIORITY ORDER (apply top-down, stop at
first match)"*, while `reference/taxonomy_rules_extracted.txt` §4 says the order is
overridden by the most-contestable element. Under strict stop-at-first, TEMPORAL
(rank 2) beats QUANTITATIVE (rank 3) whenever a date appears anywhere — which looked
like a complete explanation of TEMPORAL precision 0.56 at recall 1.00.

|---|---|---|---|---|

| V1 + §4 override | 111/125 = **88.8%** | 13/21 = **61.9%** [40.9, 79.2] | 0.87 | 0.72 |

**Identical overall accuracy.** 7 claims re-typed: 3 errors fixed, 3 errors created,

was **bought with recall** (1.00 → 0.87): V1 discarded two claims a human *did* call

**Why the 65-claim run looked like a win and wasn't.** On the held-out 65, V1 took
TEMPORAL precision 0.67 → 1.00 and overall 95.4% → 96.9%. But that rested on **4 gold
TEMPORAL claims** — 4/4 = [51%, 100%]. The full set has 27 TEMPORAL predictions, and
the effect vanishes. This is the clearest in-project demonstration of why the
never-quote-a-bare-100% rule exists: the small-n result was noise that pointed the
opposite way from the truth.

### The real finding: §4's tie-break table has a GAP

**8 of V0's 14 errors are TEMPORAL predicted where a human said RELATIONAL** — the
single dominant error class, and **V1 does not touch one of them.** They are narrative
process claims that happen to carry a date:

    Home prices fell after 2006.
    Buddhism spread from India to China during the 1st century CE.
    The Black Death plague traveled from Central Asia to Europe in the 14th century.
    Maritime trade routes replaced land travel after 1453.

The verb is a process (`fell`, `spread`, `traveled`, `replaced`) so the human read
RELATIONAL; a date is present so the classifier read TEMPORAL.

**§4 lists exactly two tie-breaks: QUANTITATIVE vs TEMPORAL, and EA vs RELATIONAL. It
has no rule for TEMPORAL vs RELATIONAL** — which is the most common confusion pair in
the actual data. So the taxonomy does not under-specify *how* to break this tie; it
never states that the tie exists. Neither V1 nor V2 can fix it, because neither
addresses that pair.

This reframes the defect: **not a prompt-wording omission but a genuine gap in the
taxonomy**, discovered by measurement rather than by reading the rules. It is a
finding for the thesis, not merely a bug.

**Untested proposal (V3):** add *"RELATIONAL BEATS TEMPORAL when the dominant verb
describes a process and the date is when it occurred."* Author's decision — it edits
the taxonomy, not just the prompt.

**Also fixed here:** `classify()` had no retry, so one transient failure killed a
125-call run (an `HTTPError` at ~130 and a `ReadTimeout` at ~30 both did). Now 5
attempts with 2/4/8/16/32 s backoff, successes only cached, checkpoint every 10.

**V2 remains unrun** (rate-limited). It targets EA vs RELATIONAL, which is 1 of 14
errors, so its ceiling is +0.8pp.
