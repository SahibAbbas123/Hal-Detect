  1. Does an LLM-with-search make the verifier ensemble useless?

  Not useless, but the threat is real and you should not answer it the
  comfortable way.

  The comfortable answer is "manual checking doesn't scale, so automation wins."
  That's true but it dodges the actual question, which isn't manual vs. 
  automated — it's my automation vs. the LLM's automation of the same check.
  That's an empirical question, and right now your thesis is arguing against an
  opponent you haven't measured.

  Three things genuinely separate your approach, in descending order of
  strength:

  Independence (strongest, and you're underusing it). If GPT hallucinates a
  claim and you ask GPT-with-search to check it, the errors are correlated —
  same parametric priors, same training data, same sycophancy toward
  confidently-phrased inputs. A SPARQL query against Wikidata has zero
  correlation with the generator. That's a methodological argument, not a
  performance argument, and it's the one that's hardest to attack. Detection
  literature takes this seriously.

  Attributable failure. Your verifiers fail in enumerable ways: retrieval missed
  the passage, NLI threshold miscalibrated, entity resolved to the wrong QID,
  property unmapped. Every one is a named, loggable, fixable class. An LLM
  reading the same source fails by producing "FALSE, because [plausible
  sentence]" where the sentence may be invented — unbounded and untraceable. The
  Panama Canal / Rosetta Stone bug is your evidence for this. You found it
  because the pipeline was decomposed. An LLM verifier making the identical
  error would have emitted a confident paragraph and nobody would ever have
  known. That's not a hypothetical advantage; it already happened in your own
  project.

  Determinism and cost. Same claim → same verdict, forever. An LLM's verdict
  drifts across model versions, which makes reproducibility of your thesis
  results impossible if the verifier is a frontier model. And a SPARQL lookup is
  milliseconds and free.

  Now the uncomfortable part: on raw numbers, a search-enabled frontier model
  will probably beat you on coverage and possibly on accuracy. HalDetect's best
  type is 80.77% at 55.32% coverage; two types are at zero. If you report a
  single global accuracy you will lose that comparison badly. The thesis
  survives this only if it's framed as "structured verification trades coverage
  for auditable, independent, reproducible verdicts" — which is already what
  your CLAUDE.md says the research bet is. You just need the number to prove the
  trade is real.

  So the concrete recommendation: run an LLM-with-search baseline on the same 
  Batch 3 and Phase 2 gold sets. It's the highest-value experiment available to
  you. If HalDetect is competitive on its covered claims, that's a strong
  result. If it isn't, you learn that now instead of at the defense, and the
  contribution reframes around independence — still publishable, more honest.
  Not running it is the only losing move.

  2. Will the scores go up?

  Some, yes — but I'd push back on "greater scores" as the primary target,
  because it creates a trap you've already walked past once.

  Your QID fix reduced coverage, 8.3% → 0% on TEMPORAL. If the objective
  function is "bigger numbers," that fix looks like a regression, and the
  incentive is to revert it. It obviously shouldn't be reverted — it converted
  two confident-wrong verdicts into honest gaps. So make that a reported metric:
  confident-wrong verdicts went 2 → 0 on Batch 3. That's a real improvement,
  it's defensible, and it aligns the metric with the honest engineering move
  instead of against it.

  Where actual score gains are available: TEMPORAL/EA coverage is a
  property-mapping problem, and it's the clearest win on the board — Wikidata
  triples are precise, so accuracy on newly-covered claims should be high.
  RELATIONAL's 80.77% is already respectable; its 55.32% coverage is the softer
  number and harder to move. And report per-type, always. A global number
  averaged across a broken CITATION verifier and a nonexistent QUANTITATIVE one
  will look terrible no matter what you do to the working parts.

  3. Root-cause analysis

  Agreed, and it's already paying off in your project. Run it on the current
  bottleneck:

  ▎ TEMPORAL coverage is 0% → 25/34 claims hit an unmapped property → 
  ▎ PROPERTY_TO_WIKIDATA is a static hand-written dict → because the design 
  ▎ assumed claim predicates form a small closed set → but free-text claims 
  ▎ produce open-vocabulary predicates → root: predicate mapping is treated as a
  ▎ lookup problem when it is a matching/retrieval problem.

  And on the bug you just fixed:

  ▎ Wrong entity chosen → "has the property" was the acceptance test → 
  ▎ resolution and lookup were fused into one step → root: a correctness check 
  ▎ was used as an identity check.

  Both roots have the same shape — a convenient proxy substituted for the 
  quantity actually of interest. That's a generalizable finding about building
  verification pipelines, and it's the kind of observation that makes a thesis
  feel like research rather than engineering notes. Worth stating explicitly in
  the writeup.

  4. Wikimedia vs. Wikidata — and no, not a rework from scratch

  "Wikimedia" is several different things, and the distinction matters:

  - Wikidata SPARQL — what you use now. Precise, but you must guess the PID in
    advance. Hence the 25/34 failures.
  - Wikidata wbgetentities — returns all statements for an entity in one call.
  - MediaWiki / Wikipedia REST — full article text, already used by RELATIONAL.

  The move that helps is the second one, and it's not a rewrite — it's a change
  to your property-lookup function. Instead of "query Q7350 for P571," fetch
  Q7350's full statement set and rank its ~50 statements against the claim's
  predicate. That converts "did I guess the right PID" into a matching problem,
  and you already have SBERT loaded from the resolution fix.

  The strong argument for it: it would have caught both known bugs. Panama
  Canal's P1619 and Rosetta Stone's P186 would both have been sitting right
  there in the returned statement set. The fix your architecture already needs
  is the same fix that would have prevented the bug you just spent time on.

  Caveat per your standing rule — I haven't opened the SPARQL code to confirm
  how cleanly resolution and lookup are separated. CLAUDE.md says resolve_entity
  now commits before querying, which suggests the seam exists, but I'd verify
  that before sizing it.
