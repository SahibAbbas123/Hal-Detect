## 1. Why the row is not a negative

`SYN_CITA_083` was a `source_swap` perturbation off `Q22_C01`: it rewrote the attributing
organisation **FAO → WHO** and left the assertion untouched. Gold label FALSE.

But **WHO is a co-publisher of SOFI 2023** — *The State of Food Security and Nutrition in the
World* is issued jointly by FAO, IFAD, UNICEF, WFP and **WHO**. Moving the attribution from one
co-publisher to another leaves the claim **exactly as true or as false as it already was**. The
perturbation injects no falsity, which is the one thing a negative exists to do.

A negatives set measures *whether a system detects an injected error*. A row with no injected
error cannot measure that, whatever its gold label says.

## 2. The `Q22_C01` flip changed WHY it is invalid — keep the distinction

| | base `Q22_C01` | the swap | `SYN_CITA_083`'s gold FALSE |
|---|---|---|---|
| before the flip | TRUE | injects nothing | **simply wrong** |
| after the flip (2026-08-26) | FALSE | injects nothing | **right, but by INHERITANCE from the base** |

So after the flip the label is *accidentally correct* while the row is still **useless for
measuring `source_swap` detection**, which is the only thing it was built to measure. Per R10, a
detection off an inherited falsity is not evidence the swap was caught.

> **Standing warning.** "The label is correct now" must never become an argument for restoring
> this row. The label was never the problem.

## 4. How to read all of that: a caution, not a benefit

Every changed figure moved **in its own system's favour, by under 2pp** — baseline CITATION
+0.9pp, baseline ALL +0.8pp, L1b +1.5pp. **Not one numerator changed anywhere in this document.**
The baseline scored the dropped row TRUE @0.733 (off retrieval about the Brookings Institution and
US figures) and L1b returned UNVERIFIABLE, so both **missed** it: removing it deletes a miss, it
does not add a detection.

Three consequences to carry:

1. **No measured detection was invalidated.** Denominators only.
2. **The base-rate gap tightening (0.0058 → 0.0045) is NOT corroboration.** It is the mechanical
   result of deleting a row the baseline got wrong. The base-rate argument rests on the flip's
   independent confirmation and on J = +0.330; #23 merely points the same way. Quoting it as
   evidence would be circular.
3. **The Wilson CIs still overlap heavily.** L1b 37.5% [21.2, 57.3] vs baseline CITATION 21.7%
   [9.7, 41.9]; ALL 54.4% [42.7, 65.7]. n = 24 cannot separate 37.5% from 21.7%, so the clean
   prior-independent part of the L1b result remains **FPR 0/24 vs 2/24** and the **0 confident
   errors**, not the TPR gap. R11's concentration caveat (8 of 9 from one Wikidata item) stands
   verbatim at the new numbers.

## 5. Two denominator bugs the removal exposed — the reusable part

### 5.1 A row removal that corrected nothing (now CLAUDE.md R1a)

The plan's premise was that deleting the row from `synthetic_negatives.csv` — the file whose name
describes the population — would make every corrected denominator automatic. **It did not.**
`negatives_cache_audit.py` builds its population from **`nonrouted_negatives_results.csv`**, a
*results* file, and opens the source only to look up `base_claim_id`. So after the deletion:

* every published denominator was still 85;
* the source lookup had a new **orphan**, which `if not base: continue` swallowed **in silence**.

A data edit that looked applied, changed no output, and quietly degraded a lookup. It surfaced only
because `--selftest` asserted `len(a.neg) == 84` and failed with `n=85`.

**Rules this produced.** Verify a deletion by *a number moving*, not by the row being gone. Read
the loader, not the filename, to learn where a denominator comes from. And when a fix rides on a
silent skip, **make the skip loud**.

### 5.2 The mechanism actually used

`synthetic_negatives.csv` is the **single authority on membership**; the audit **filters its
results join through it**. The results CSV is never rewritten. Three reasons at once:

* **R19** — a quoted result CSV is never overwritten;
* the dropped row's scored verdict stays on disk as the **evidence** that dropping it costs no
  detection (§4) — deleting it would destroy that audit trail;
* one edit per future drop instead of two.

Because a silent filter is itself the bug being fixed, the filter is guarded by a named `DROPPED`
constant carrying the full reason, and an **unrecorded orphan raises `SystemExit`** rather than
being quietly excluded — once counts are printed, a deliberate drop and a data bug look identical.
Two selftest checks assert the mechanism in both directions: *out of the counted population*, and
*still present in the results file as evidence*. **Never widen that check to make a run pass;
record the drop in `DROPPED` with its reason.**

### 5.3 Two sets, one count, and a coincidence that hides the error (now R1b)

Two docstrings read "0 of 69 non-colliding rows". Non-colliding is 85 − 16 = **69** pre-drop. But
the audit's `control_n` is a **different set** — rows with a locatable base that are not
same-key-and-entail-matched — which *also* printed 69. Post-drop they separate: **68** vs **69**.

Both numerators are 0, so the control holds either way and nothing measured was wrong. The hazard
is a reader reconciling the two and "fixing" the one that was already right. **State which set a
denominator counts, not just its size.**

A second instance of the same shape: CLAUDE.md §5 used to warn that a wrong-denominator
reconstruction gives **CITATION 23**, as the *symptom* of the bug — and **23 is now the correct
post-drop value**. The number that used to diagnose the error is now the right answer, so it
diagnoses nothing in either direction. Run the script; do not reconstruct these by hand.
